Your app is leaking API keys. Probably.

Anyone can open your site, press Inspect, and copy the keys inside. LeakLock reads exactly what your site sends every visitor and finds them, even keys for APIs no scanner has heard of.

Works on any site: Lovable, Bolt, Vercel, Netlify or your own domain. Keys are always shown masked.

The part others miss

Not every key starts with sk-

Pattern scanners only know key formats they've been taught. Plenty of smaller AI and image APIs hand out plain random strings. LeakLock catches a key by how your code uses it, then names the API from where the request goes.

Pattern-only scannerfetch("https://api.kie.ai/v1/jobs", { headers: { Authorization: `Bearer ${e}` } }) // e = "d41f8b…a07c" (32 hex chars, no prefix) ✓ No secrets found …because it has never seen this format.
LeakLockfetch("https://api.kie.ai/v1/jobs", { headers: { Authorization: `Bearer ${e}` } }) SECRET kie.ai API key d41f…a07c sent as a Bearer token to api.kie.ai traced through minified variable `e` → fix steps + a prompt for your AI builder
How it works

See your site the way an attacker does.

01

Reads what ships

The HTML, every JS bundle, lazy-loaded chunks and public source maps. Not your repo: what visitors actually download.

02

Finds any key

30+ providers by shape, plus any API by usage: Bearer tokens, API-key headers, ?key= in URLs. Minified variables are traced back to their value.

03

Tells you the fix

Plain steps, and a ready prompt to paste into Lovable, Bolt or Cursor that moves the call to a server without changing how your app works.

✓

No false alarms

Stripe pk_, Supabase anon and Firebase web keys are public by design, and we say so. Supabase JWTs are decoded to tell anon from service_role.

✓

Never shows a full key

Everything is masked. The checker stores nothing, rate-limits, and refuses private addresses, so it can't be used to harvest keys.

✓

Zero dependencies

One small Node package you can read in an afternoon. MIT licensed.

For developers

Gitleaks checks your repo.
LeakLock checks what you ship.

A key can be clean in git and still end up in your bundle through a VITE_ or NEXT_PUBLIC_ variable. Catch it before it goes live.

# any live site or build folder
npx leaklock scan myapp.com
npx leaklock scan dist/ --fix

# fail CI if a secret ships
npx leaklock scan dist/ --fail-on=secret
# .github/workflows/leaklock.yml
- run: npm run build
- uses: sgroy10/leaklock@v1
  with:
    target: dist
    fail-on: secret
Straight talk

Two things no tool can change.

A key in the browser can't be hidden.

Obfuscation, splitting and in-browser encryption all fail: the key shows in the Network tab the moment it's sent. The only fix is that the real key never reaches the browser.

A key that was public may be copied.

Moving it to a server stops new copies. Rotating it is the only way to cut off anyone who already took it. That's your call; we'll tell you the risk plainly.
