Not every key starts with sk-

Most scanners match key formats they've been taught. Many AI, image and voice APIs issue plain random strings, so those keys go straight through. LeakLock also looks at how your code uses a string.

Authorization: Bearer

A value sent as a bearer token.

x-api-key

A value in any API-key style header.

?key=

A value passed as a key in a URL.

It follows minified variables back to their value, and names the API from where the request goes.

Every finding comes with the fix.

Not just "rotate your key." You get the steps, and a prompt to paste into the tool that built your app.

  1. Move the call to a server. A small function in Supabase, Vercel or Netlify makes the request instead of the browser.
  2. Store the key as a secret on that server, never in a VITE_ or NEXT_PUBLIC_ variable.
  3. Scan again to confirm it's gone from what you ship.
  4. Consider rotating. If the key was public, someone may already have a copy.
Paste into Lovable, Bolt, Cursor or v0My app exposes a kie.ai API key in the browser bundle (found in assets/index-4f2a9c.js, sent to api.kie.ai). Anyone can copy it. Fix this without changing how the app behaves: 1. Create a server-side function (use a Supabase Edge Function if this project uses Supabase, otherwise a serverless function on our host) that makes the same kie.ai request, reading the key from a secret named KIE_AI_API_KEY. 2. Replace the browser's direct call with a call to that function, passing the same inputs and returning the same response shape. 3. Remove the key from all frontend code, .env files with VITE_ or NEXT_PUBLIC_ prefixes, and constants. 4. Only allow requests from our own site and add a basic rate limit. 5. Do not change any UI, routes or other logic. List every file you changed.

The prompt never contains your key.

Questions

Is it safe to paste my URL here?

LeakLock only downloads the public files any browser would load from your site. Keys are masked before they leave the server, nothing is stored, and private or internal addresses are refused. Prefer your own machine? Run npx leaklock scan yourapp.com.

It found my Supabase anon key. Is that a problem?

No. The anon key is meant to be public. What protects your data is Row Level Security on every table. The service_role key is different: it bypasses all security, and LeakLock marks it critical.

Can't I just hide the key in the frontend?

No. Obfuscating, splitting or encrypting a key in the browser doesn't work, because the real key appears in the Network tab the moment it's sent. The only fix is that the key never reaches the browser.

Do I have to create a new key?

Moving the call to a server stops new copies. A key that was already public may have been copied, and rotating it is the only way to cut that off. LeakLock tells you the risk; the decision is yours.

"No keys found." Am I safe?

It's good news, not a guarantee. Keys hidden in unusual ways can be missed, and LeakLock doesn't test your database rules or server code.

Can I scan someone else's site?

Only scan sites you own or have permission to test. If you find a leak on someone else's site, tell them privately.
